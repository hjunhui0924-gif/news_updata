# 知更前端渐进式优化方案

## 1. 文档目的

本文档用于指导 `news_updata` 的整套前端优化，从现有可运行的阅读器逐步演进为视觉统一、交互完整、响应式可靠、可持续维护的产品界面。

优化以现有实现为基线，不迁移框架，不重写业务数据层，不复制外部产品的品牌或内容。所有改动都应保持现有路由、API、权限边界和数据含义不变，除非某一轮明确记录了产品决策。

当前技术基线：

- Next.js 16、React 19、TypeScript 5.9；
- pnpm 11；
- Tailwind 4 已安装，但当前主要使用 `src/app/globals.css` 和组件 class；
- Radix Dialog、`lucide-react`、自定义 Button 原语；
- 页面入口为 `src/app/[[...path]]/page.tsx`；
- 主界面由 `src/components/reader-app.tsx` 组合，数据列表、详情、订阅、Trending、Skill、设置等均已有独立组件；
- 已有 Vitest、Playwright、ESLint、TypeScript 检查和演示数据模式。

## 2. 优化目标和边界

### 2.1 目标

1. 让用户在首次进入时明确知道当前位置、主要任务和下一步行动。
2. 让“发现更新 → 筛选 → 阅读 → 收藏/标记已读 → 回到列表”的核心路径稳定、快速、可恢复。
3. 建立可复用的语义设计 token，减少 4000 行全局样式中的重复和散落字面值。
4. 覆盖加载、空结果、筛选无结果、部分失败、权限不足、提交中、成功和可重试错误。
5. 在桌面宽屏、普通笔记本、平板和窄手机上保持可读、可操作，不依赖 hover 才能完成任务。
6. 保证键盘、屏幕阅读器、焦点、对比度、触控尺寸和 reduced-motion 行为可接受。

### 2.2 不在本轮范围内的内容

- 不更换 Next.js、React、CSS 方案或数据库；
- 不修改 GitHub OAuth、订阅同步、AI 任务和后台 Worker 的业务规则；
- 不把演示数据伪装成真实数据；
- 不为视觉改动引入新的 UI 框架；
- 不以一次性大规模重写代替分批可验证的改动。

## 3. 统一执行方法

每个模块都按下面的生命周期推进。没有完成当前轮的验收门禁，不进入下一轮。

### 3.1 开发前契约

在改代码前，在 PR 或对应任务记录中写清楚：

- 本轮用户流程、主操作、辅助信息、权限和失败点；
- 要修改的文件或组件；
- 选用的页面模式：数据列表、详情/设置、表单/引导、AI 工作区等；
- 数据和状态假设，尤其是演示模式、无数据和接口失败；
- 完整状态矩阵；
- 宽屏、窄屏、键盘和读屏决策；
- 不改变的业务行为和已知风险。

### 3.2 实现顺序

1. 先复用现有 Button、Dialog、图标和数据接口。
2. 先建立结构和语义 HTML，再调整 token、间距、颜色、边框和动效。
3. 先实现正常路径，再补齐状态矩阵，不把错误状态留到最后。
4. 组件内部状态变化要保留用户上下文：筛选、搜索、分页、表单值和可恢复错误不能无故重置。
5. 所有异步操作都给出 pending、成功、失败和重试反馈；破坏性操作需要确认或可撤销路径。

### 3.3 每轮开发完成后的验证门禁

每轮至少执行：

```powershell
pnpm typecheck
pnpm lint
pnpm test
```

涉及浏览器交互时，补充相关 Playwright 测试：

```powershell
pnpm test:e2e
```

若完整 E2E 依赖外部 OAuth 或真实 GitHub，则使用 demo 启动方式和现有专项配置，记录未覆盖的外部依赖，不得把“无法连接真实服务”误报为前端通过。

每轮还必须完成以下人工审查：

- 桌面宽屏至少一个视口（建议 1440×900）；
- 窄屏至少一个视口（建议 390×844）；
- 键盘 Tab、Shift+Tab、Enter、Space、Escape 流程；
- 打开浏览器控制台检查异常、React warning、网络失败；
- 检查截图或录屏，确认无溢出、重叠、跳动和截断；
- 核对 loading、empty、error、disabled、success、permission 状态；
- 进行一次代码审查，重点看状态重置、无障碍语义、响应式断点和业务请求是否被误改。

### 3.4 完成判定

一轮只有同时满足以下条件才算完成：

- 功能路径可操作；
- 相关自动化检查通过；
- 浏览器人工检查通过；
- 状态矩阵已覆盖或对未覆盖项有明确原因；
- 代码审查没有阻塞问题；
- 记录变更摘要、测试命令、结果和遗留假设。

## 4. 分阶段开发路线

### 阶段 0：基线审计和测量

**目标**：在视觉改动前锁定当前行为、页面结构和回归证据。

**范围**：

- `src/app/[[...path]]/page.tsx`、`src/app/layout.tsx`；
- `src/app/globals.css`；
- `reader-app.tsx`、`sidebar.tsx`、`feed-list.tsx`、`item-detail.tsx`；
- 现有 Playwright 配置、demo 数据、测试目录。

**开发步骤**：

1. 列出所有入口：`/today`、`/feed`、`/saved`、`/subscriptions`、`/skills`、`/settings`、`/onboarding`、`/items/:id`、`/login`。
2. 为每个入口记录正常、无数据、失败和权限状态。
3. 启动 demo，采集桌面和手机截图，记录当前布局问题、溢出、跳动和交互死角。
4. 记录组件间的状态流：视图切换、选中条目、刷新、toast、订阅弹窗、详情 tab。
5. 形成问题清单，按阻塞核心流程、影响一致性、影响无障碍、纯视觉细节排序。

**验收**：不改产品行为；所有基线页面可访问；截图、问题清单和已知测试缺口可复现。

### 阶段 1：设计 token 和基础 UI 原语

**页面模式**：基础设计系统，不单独引入页面模式。

**目标**：统一颜色、字号、间距、圆角、边框、阴影、焦点环、控件高度和动效。

**范围**：`src/app/globals.css`、`src/components/ui/button.tsx`，必要时新增小型基础原语，不改业务组件逻辑。

**开发步骤**：

1. 将现有 `:root` 变量整理为 background、surface、foreground、muted、border、focus、primary、success、warning、danger、status tint、shadow、radius、spacing、motion 等语义 token。
2. 统计字面颜色和重复尺寸，逐步替换为 token；保留确实属于品牌或状态的例外并写注释。
3. 统一按钮的 primary、secondary、ghost、danger、small、loading、disabled 状态。
4. 统一输入框、select、分段控件、icon button、标签、toast、错误提示和 loading 指示器。
5. 为 focus-visible、hover、active、disabled 和 reduced-motion 建立一致规则。
6. 确保状态颜色同时配有文字或图标，不依赖颜色 alone。

**状态矩阵**：正常、hover、focus-visible、active、disabled、pending、成功、失败；长文本和窄宽度。

**验收**：基础原语在现有页面中视觉一致，控件尺寸没有导致布局回归；键盘焦点清晰；`prefers-reduced-motion` 下无非必要动画。

### 阶段 2：应用壳层、导航和移动导航

**页面模式**：应用壳层 + 数据列表/详情的导航框架。

**范围**：`reader-app.tsx`、`sidebar.tsx`、顶部栏和移动导航相关 CSS。

**开发步骤**：

1. 明确当前路由、页面标题、面包屑、当前选中导航和计数的来源。
2. 统一品牌区、工作空间切换、主导航、订阅来源、设置入口和用户状态的层级。
3. 确定桌面侧栏固定、平板折叠、手机底部导航或抽屉的行为，不让用户失去主要入口。
4. 处理导航切换时的焦点落点、浏览器后退、详情返回列表和深链接刷新。
5. 为通知、添加订阅、Skill 入口等 icon-only 控件补齐可读名称和 tooltip。

**状态矩阵**：当前页、未读计数为 0/非 0、无订阅、演示模式、GitHub 未连接、窄屏导航展开/关闭、路由切换失败。

**验收**：任意入口可通过键盘到达；手机不依赖侧栏 hover；页面标题和导航状态始终一致；返回详情列表后保留列表上下文。

### 阶段 3：主阅读流：更新列表和详情

**页面模式**：数据列表 + 详情。

**范围**：`feed-list.tsx`、`item-detail.tsx`、`item-sources.tsx`、`bilingual-translation.tsx` 及对应 CSS。

**开发步骤**：

1. 固定列表标题、数量、搜索、类型筛选、未读筛选、来源筛选和排序的视觉层级。
2. 明确列表卡片的信息优先级：项目、更新类型、标题、摘要、时间、来源、收藏和未读状态。
3. 设计长标题、缺少摘要、多来源、历史数据和超长项目名的布局规则。
4. 优化列表到详情的选中反馈、已读更新、收藏、打开来源和返回行为。
5. 统一详情中的摘要、依据、原文、对照翻译 tab，明确当前 tab 和异步任务反馈。
6. 为“没有更新”“筛选无结果”“详情不存在”“摘要失败”“翻译排队/完成/失败”提供下一步动作。
7. 保留搜索词、筛选项、滚动和已选条目，不因刷新或可恢复错误清空用户上下文。

**状态矩阵**：初始加载、已填充、无更新、筛选无结果、部分来源、刷新中、刷新失败可重试、摘要 pending/success/error、翻译 pending/success/error、已读/未读、已收藏/未收藏、详情缺失。

**验收**：核心路径可以完整走通；卡片和详情在 390px 宽度不横向溢出；tab 可键盘操作；异步操作有 `aria-live` 或邻近状态说明；长内容不破坏布局。

### 阶段 4：订阅管理和首次引导

**页面模式**：数据列表 + 表单/引导 + Dialog。

**范围**：`subscriptions-panel.tsx`、`repository-search.tsx`、`starred-import.tsx`、`following-import.tsx`、`star-sync-panel.tsx`、`github-connection.tsx`。

**开发步骤**：

1. 将“添加订阅”拆成清晰的项目搜索、GitHub Star 导入、关注导入等入口，并保持单一主操作。
2. 统一表单标签、帮助文本、校验位置、提交中状态和错误恢复。
3. Dialog 打开后管理焦点，Escape 关闭，提交失败时保留输入和已勾选项。
4. 为搜索结果、分页、部分导入失败、重试、已存在订阅和同步中的状态提供明确反馈。
5. 为首次使用的 onboarding 说明目的、权限、预计结果和跳过/稍后处理路径。
6. 删除订阅、取消自动同步等不可逆或高影响操作要有确认和失败恢复。

**状态矩阵**：未连接 GitHub、已连接、搜索空结果、搜索失败、分页加载、选择 0 项、选择部分项目、导入中、导入成功、部分失败、全部失败、重复订阅、删除确认、权限拒绝。

**验收**：表单键盘闭环完整；错误不丢输入；导入结果能逐项解释；移动端按钮不被挤出屏幕；真实 OAuth 不可用时 demo 流程仍可验证。

### 阶段 5：Trending 和 Skill 目录

**页面模式**：发现列表 + 详情/AI 工作区。

**范围**：`trending-panel.tsx`、`skills-panel.tsx` 及其相关 CSS。

**开发步骤**：

1. 统一发现页标题、语言筛选、刷新、排名、描述、统计、订阅操作的层级。
2. 设计 Skill 来源 tab、搜索、分类/标签筛选、详情、原文、AI 摘要和双语视图。
3. 将 Skill 详情拆成清晰的信息区：来源、用途、正文、AI 状态、依据和下一步操作。
4. 对 AI 任务明确未启用、排队、生成中、完成、失败、超长内容和费用/权限提示。
5. 确保发现列表和 Skill 卡片在窄屏变为单列，详情操作可滚动且不被固定元素遮挡。

**状态矩阵**：加载、缓存数据、过期数据、空榜单、筛选无结果、接口失败、AI 未启用、AI 生成中、AI 成功、AI 失败可重试、原文缺失、来源链接失效。

**验收**：不把 AI 状态只表达为颜色；长 Skill 名称和标签可换行；tab、筛选、详情返回可键盘完成；外链有清晰名称。

### 阶段 6：设置、通知、登录和异常体验

**页面模式**：详情/设置 + 表单 + 权限状态。

**范围**：`settings-panel.tsx`、`login.tsx`、通知预览、全局 toast/banner 和相关 CSS。

**开发步骤**：

1. 按阅读偏好、同步状态、连接状态、站内简报等主题分组设置。
2. 为开关、时区、保存、重置和加载状态定义可理解的标签与当前值。
3. 处理保存成功、保存失败、网络恢复、未保存变更和重新加载后的状态同步。
4. 登录页区分 GitHub 未配置、访问被拒绝、会话过期和普通网络失败。
5. 统一全局 toast、inline error、banner、`aria-live` 的使用边界，避免重复或无法感知的反馈。

**状态矩阵**：未加载、已加载、修改未保存、保存中、保存成功、保存失败、权限拒绝、会话过期、GitHub 断开、通知为空、通知生成失败。

**验收**：设置修改不会静默丢失；错误有恢复动作；登录和权限信息不泄露敏感数据；读屏用户能获得与视觉用户等价的反馈。

### 阶段 7：全局收尾、性能和一致性治理

**目标**：把分模块结果收敛为长期可维护的前端规范。

**开发步骤**：

1. 删除重复 CSS，按 token、原语、壳层、页面模块和响应式规则整理 `globals.css`。
2. 检查所有页面的 heading 层级、按钮名称、表单 label、链接文本、焦点样式和对比度。
3. 检查所有固定高度、绝对定位、overflow、`z-index` 和移动端断点，修复动态内容导致的布局跳动。
4. 对主要交互补齐 Playwright 回归用例，优先覆盖导航、搜索筛选、详情 tab、收藏/已读、订阅导入和设置保存。
5. 对共享组件补充有意义的单元测试，避免只测试静态渲染或重复实现细节。
6. 对慢请求和轮询页面检查请求频率、pending 反馈、取消/重试和页面卸载后的状态更新。
7. 生成最终桌面/移动截图，与阶段 0 基线对照，记录仍需产品决策的问题。

**最终门禁**：`pnpm typecheck`、`pnpm lint`、`pnpm test`、相关 `pnpm test:e2e*` 全部通过；主要页面桌面/移动人工 QA 通过；没有阻塞级控制台错误、横向溢出、键盘死路或无法恢复的核心流程。

## 5. 推荐的模块交付顺序

建议按以下顺序建立独立 PR 或独立提交，每个模块完成后再合并：

1. 阶段 0 基线审计；
2. 阶段 1 token 和 UI 原语；
3. 阶段 2 应用壳层和导航；
4. 阶段 3 更新列表和详情阅读；
5. 阶段 4 订阅、导入和 onboarding；
6. 阶段 5 Trending 与 Skill；
7. 阶段 6 设置、登录、通知和异常；
8. 阶段 7 全局清理、回归和发布前审查。

每个 PR 只处理一个阶段或一个明确的垂直切片。若一个阶段需要拆分，优先按用户流程拆分，例如“列表视觉结构”“详情状态”“翻译反馈”，不要按 CSS 文件机械拆分。

## 6. 每轮 PR / 代码审查模板

提交 PR 时必须包含：

```text
## 用户流程
- 入口：
- 主操作：
- 预期结果：

## 改动范围
- 组件/样式：
- 是否触及 API 或业务状态：是/否

## 状态覆盖
- [ ] loading
- [ ] populated
- [ ] empty
- [ ] filtered-empty
- [ ] pending
- [ ] success
- [ ] recoverable error / retry
- [ ] disabled / permission denied

## 响应式与无障碍
- [ ] 桌面视口
- [ ] 390px 窄屏
- [ ] 键盘操作
- [ ] focus-visible
- [ ] label / heading / live region
- [ ] reduced motion

## 验证
- 命令：
- 结果：
- 手工检查：
- 未覆盖与原因：
```

审查者重点确认：

- 是否误改业务请求、权限或路由行为；
- 是否出现状态更新后丢失用户上下文；
- 是否把错误只显示成颜色或只写进控制台；
- 是否引入新的重复 token、重复组件或无必要依赖；
- 是否在移动端隐藏了完成任务所需的唯一入口；
- 是否为异步操作和破坏性操作提供反馈、确认或重试；
- 是否有足够的测试证据，而不是只依赖截图。

## 7. 手工 QA 清单

### 核心阅读路径

- [ ] 从 `/today` 进入更新详情；
- [ ] 搜索项目、作者和正文关键词；
- [ ] 切换更新类型和未读筛选；

## 8. 完成后的交付物

整个优化结束时应留下：

- 本文档及每轮 PR 的实施记录；
- 一份最终 token 和组件使用说明；
- 主要页面桌面/移动截图或测试报告；
- Playwright 核心回归用例；
- 已知限制、尚未解决的产品决策和后续维护建议；
- 最终验证命令及结果。

完成标准不是“所有页面看起来一样”，而是核心阅读和管理流程在不同状态、不同屏幕和不同输入方式下都能被理解、完成并恢复。
