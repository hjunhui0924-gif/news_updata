## U2：后台公平性、限流与恢复

- 阻塞实验先复现旧共享消费者的问题：模型挂起后 GitHub 任务超过 2 秒仍不能开始。保留同一持久队列，使用 pg-boss 精确优先级消费，为 AI、GitHub、YouTube 各保留一个消费者，总任务并发最多 3；不增加业务数据库连接池。发布每类最多 16 个，避免大量 AI 待办挡住其他类型的 outbox。
- 最后一次隔离 PG 队列实验：AI/YouTube 持续 gate、40 个 AI 待办时，GitHub 首任务等待 505 ms；同批 12 个 GitHub 任务等待 p95 6,086 ms，均在预先设置的首个 2 秒、整批 8 秒预算内。这是单次本机批次实验，不是生产延迟。旧优先级 0 投递保持原位并自然排空，不能承诺旧积压在升级时立即获得新通道。
- 400 来源的调度状态读取从 401 次 SQL 改为 1 次关联扫描；诊断单样本约 449.78 ms → 2.40 ms，不作为百分位。每轮最多排入 50 个到期来源，优先较久未调度者，仍遵守禁用与 retryAt。
- YouTube 项目配额错误使用 PostgreSQL 持久冷却，按 OAuth client / API key 的哈希隔离、原子延长但不缩短，重建 transport 后有效；401 与账号限流不写项目级冷却。无法确认两个不同凭据属于同一项目时不强行合并，也不明文保存凭据。来源级持久 retryAt、分页断点与条件请求继续保留。
- 独立 review 发现 AI 与同步并行会丢失新正文的摘要任务；已补持久版本意图与原子后继任务。第二轮又发现开始前已更新的正文可能在中断后重复付费；已在模型请求前按锁定快照消费已接手意图，只有之后的正文更新能生成后继。两条 gated 模型/真实 persistUpdates 回归均先红后绿，保留账目结算与去重断言。
- 最后相关 7 文件 16 项测试通过；此前平台、条件请求与 OAuth 的 48 项相关测试通过（最终全量仍待 U7）。最新类型与改动范围 Lint 通过。队列去重、旧投递、重启恢复与配额隔离均有回归；最终只读复审通过，进入 U3。

## U5：AI 退化与版本一致性

- PG 回归先复现模型切换仍返回条目旧摘要，再增加各类结果的 opaque 配置版本（模型、提供方、thinking、目标语言、提示词版本）。沿用原缓存键；内容 hash 条件回写与 summary / translation 版本合并同一 SQL 完成，版本在发起模型调用前捕获。
- 启用 AI 时，列表、详情及手动排队统一隐藏版本不匹配或无版本的真实历史结果，等待用户手动重新生成；读取不自动排任务、不扣费，也不删除旧数据。关闭 AI 仍允许读历史缓存，Demo 与中文原文的本地翻译保持原行为。原文更新后的旧结果不会覆盖新正文。
- 退化矩阵：关闭 → 原文可读、生成禁用；排队/慢模型 → 原文、已读和收藏可用；预算拒绝 → 不调用模型；无效返回 → 不保存结果，已返回的调用按 settled 记账；超时 → 保留 uncertain 费用，不能当免费自动重试；进程中断的 reserved 仍计入预算，需人工供应方对账。U2 的版本交接避免同版本中断自动再次付费。
- 6 文件 54 项相关单元/隔离 PG 测试、6 项 AI 浏览器测试通过；模型慢时的真实数据库读/收藏和浏览器四种退化场景均覆盖。无视频全文 AI 任务，输入仍为受控来源片段，输出不能执行订阅或源站写操作。
- next typegen、类型与改动范围 Lint 退出 0；独立 review 无 Critical / Important 或必须修复 Minor，进入 U6。
