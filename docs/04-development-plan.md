## 当前优先级：先做好 GitHub

用户明确要求先完善 GitHub，再做其他平台接入。目标是「打开一个网页，知道我关注的人和项目有哪些更新，并尽量直接读完」。以下为后续路线，本轮先完成下文的关注范围增量，不代表 G1–G4 全部完成。

| 顺序 | 模块 | 用户结果 | 验收重点 |
| --- | --- | --- | --- |
| G1 | 关注对象管理 | 容易导入关注的人，能区分作者、仓库与 Star 来源，明确每种订阅跟踪什么 | 已完成：following 分页、重复/部分失败、名额限制、跟踪范围提示 |
| G2 | 同步可靠性与反馈 | 能分清尚未检查、正在检查、检查后无更新、同步失败；重启后继续同步 | 检查时间、队列/Worker 状态、限流/离线恢复、分页续扫、去重与状态保留 |
| G3 | 站内阅读闭环 | 从作者发现项目后可选择订阅版本；正文、图片、相对链接与对照翻译可用 | 作者到仓库订阅、Markdown 来源路径、图片加载失败、长内容/手机阅读 |
| G4 | 持续使用验证 | 实际关注对象连续使用时没有未解释的漏抓和重复，内容与状态可信 | 支持范围内与源站抽样比对、发布到入库延迟、原文/译文完整性、调用与费用记录 |

Trending 保留在今日精选，主线资源优先投入已有关注的更新体验。暂缓个性化推荐、自动质量打分和完整的其他平台适配；当前只整理 X / RSS 预研说明。GitHub 的 commit、PR、Issue、预发布等不因本次优先级调整自动全部加入信息流；需要按真实使用需求逐类确定范围，避免增加噪声。

### G1 实施结果

following 管理现已支持每页 50 人的分页读取、当前登录账号快捷读取和手动输入公开账号；预览结果包含当前页、下一页和已订阅状态。作者订阅继续跟踪新建公开非 fork 仓库，以及公开事件中由本人发布的正式 Release。仓库订阅跟踪正式 Release，不代表作者所有活动。

本轮修改范围：`src/server/connectors/github.ts`、`src/server/connectors/github-user.ts`、`src/app/api/github/following/*`、`src/server/subscriptions/following.ts`、`src/components/following-import.tsx`、`src/components/subscriptions-panel.tsx` 及相关共享类型和测试。

- following 预览包含 `page`、`nextPage`、`truncated` 和 `subscribed` 字段，并复用当前用户 GitHub 连接器。
- 登录账号可以留空用户名直接读取；用户仍可手动输入公开账号，浏览列表不会直接改变订阅。
- 跨页选择不丢失，已订阅对象禁选，导入按首次出现的用户名去重。
- 批量导入返回结构化部分失败结果，成功项保留，失败项可重试；数据库集成验证了幂等和任务写入。
- 作者订阅上限在 UI 中提前提示，达到 50 个时不再勾选或导入新作者。
- 作者和仓库订阅的覆盖范围就地说明，不把「作者关注」描述成自动订阅他的全部项目版本。
- 暂不把 GitHub 取消关注等同于应用取消订阅；自动跟随增删策略单独确定。

本轮 G1 验证：following 单元/集成测试通过，4 项 following 浏览器测试通过；全量测试为 27 个测试文件、149 项通过，类型检查、Lint 和 Web/Worker 构建通过。

测试与停止条件已满足：connector 分页/鉴权/错误契约、数据库幂等和部分失败、跨页勾选、已订阅状态、名额不足、手机无横向溢出均已覆盖。G1 完成后进入 G2，不把短期测试等同于长期连续试用。

### 下一模块 G2 的实施边界

下一步聚焦同步可靠性与反馈：统一显示尚未检查、正在检查、已完成、部分完成、限流等待、授权失败和 Worker 离线；确认重启后任务、分页续扫、失败重试、检查时间、去重和阅读状态保留。先做状态契约和 Worker/数据库测试，再补订阅管理 UI 与浏览器回归。

### 扩展其他平台前的条件

- GitHub 导入关注、同步更新、站内阅读、已读/收藏这一完整流程可重复使用；G1 关注导入已完成，G2～G4 仍待完成。
- 承诺的更新种类和同步频率明确；失败能看见，恢复能验证，不承诺 GitHub 全部活动无遗漏。
- 至少连续 7 天实际试用，记录并处理重复、延迟和支持范围内的漏抓；时间尚未经过不能以单次测试代替。
- 依据实际试用结果判断 GitHub 日常阅读是否足够可用，再评估下一平台的内容覆盖、接入成本与限制。当前 X 只做官方资料和最小读取验证，RSS/Atom 可作为较低风险的抽象验证平台。

每个后续模块仍执行实现、测试、审查的闭环。公开部署按用户选定的主机另行处理；暂不实现邮件、公开注册或收费体系。

### 本轮交付：区分项目更新与博主更新

按用户最新确认，先明确两种关注对象的行为：项目跟踪正式版本及已收录说明修改，博主跟踪新项目与本人发布的正式版本。连接器通过测试后，完成两条流的分页续查、多来源并发去重与阅读状态保留，再完成来源标识、跟踪范围说明和「查看更新」入口。审查补充重复同步历史上限、事务取消两项修复。

接口窗口、归属规则、验证结果和实际登录限制见 [本轮交付记录](11-github-following-scope.md)。长期试用仍是后续路线中的 G4 工作。

后续已补充 G2 的授权恢复部分：令牌按需自动续期、跨进程串行轮换、临时失败重试、授权状态和重新连接入口。真实账号续期与同步恢复已验证，细节见 [授权续期记录](12-github-auth-renewal.md)，不代表 G2 全部可靠性场景已完成。

## 跨平台预研模块

跨平台预研不替代 GitHub G1～G4，也不直接改变现有数据结构。先统一“平台、来源、订阅、更新条目、连接器”的领域语义，再评估 X 或 RSS 适配器。

| 阶段 | 目标 | 停止条件 |
| --- | --- | --- |
| P0 文档与准入 | 记录 X/RSS 范围、风险、官方验证项 | GitHub 7 天试用或范围定义未完成 |
| P1 统一来源接口 | 让 GitHub 通过平台无关语义工作 | 唯一键、编辑/删除和同步状态没有明确规则 |
| P2 隔离适配器 | 用 fixtures 和可注入 transport 验证 X/RSS | 分页、限流、鉴权、去重、恢复任一项不稳定 |
| P3 用户功能 | 再加入平台选择、来源管理和阅读器入口 | 没有真实接口证据或成本/权限不可接受 |

详细范围见 [跨平台扩展预研](14-platform-expansion.md)。
