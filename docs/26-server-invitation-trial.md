# 服务器邀请试用版：多用户边界与上线运行

日期：2026-11-05。目标是把现有聚合平台部署到服务器，让受邀用户使用自己的 GitHub 账号登录，再按需连接自己的 YouTube 账号。保留现有聚合、阅读、订阅、GitHub Star Skill 等功能；不新增公开注册、付费套餐或管理员后台。

本轮只处理多用户及运行边界，**不代表已完成正式安全审计、公开注册服务验收或 YouTube 内容生命周期**。后者按用户决定暂缓，缺口见 [真实闭环与生命周期验收](25-youtube-live-acceptance.md)，不能因容器上线而标记完成。G4 持续试用也单独记录。

## 1. 已实施的边界

| 范围 | 行为 |
| --- | --- |
| 登录准入 | 使用 GitHub 稳定数字 ID 邀请名单；每次读取会话后重新检查准入，不按昵称或邮箱合并账号 |
| 私有数据 | 订阅、条目、阅读状态、偏好、通知、任务和授权凭据按当前登录用户查询；客户端传入别人的条目或来源 ID 不能跨用户读写或触发任务 |
| 服务器文件 | 公网部署的本机 Skill 列表、详情和 AI 路径在服务层拒绝访问；页面只提供用户自己的 GitHub Star 来源。Worker 同样经过服务层，不仅隐藏 UI |
| 凭据 | 公网部署拒绝共享 `GITHUB_READ_TOKEN`；各账号使用自己的 OAuth。Web/Worker 只获得应用数据库密码，不获得数据库管理员密码 |
| 写请求 | 校验本站 Origin；成功及失败响应均不允许缓存；反向代理不配置页面或 API 缓存 |
| 限频 | 业务接口以用户 ID 和固定操作类别在数据库原子计数，跨标签页和 Web 进程共享；外部解析与 AI 独立于本地阅读/状态写入 |
| 预算 | 所有 AI 入口共用用户及整站日/月预算预占；固定锁序防止不同用户并发超额预占，不确定费用继续占用预算 |
| 移除邀请 | 重启 Web/Worker 应用更新后的名单，旧会话不再获得业务访问；后续调度跳过该用户，已排队任务执行前复查，不生成后继摘要任务 |
| 队列 | 按平台保留处理通道；发布批次按用户轮次和持久的最近服务记录选取，避免后来的用户一直被旧积压挡住 |

默认每用户每分钟限额：读取 600、本地写入 60、外部接口操作 30、AI 操作 10。直接添加来源、关注预览/导入、搜索及撤销等请求纳入相应类别；后台持续同步另受调度、去重和提供方额度控制。自身限频返回 429、`Retry-After` 和可读提示，仍可进行未耗尽的本地阅读操作。登录接口使用认证库的生产限频；代理覆盖客户端伪造的转发 IP。

默认 AI 用户预算为日 0.5 / 月 5，整站为日 5 / 月 50，均为配置中的 USD 估算额度；供应商实际结算可能不同，应另外配置供应商账户硬额度。整站额度不能用增加用户数绕过。默认真实模型关闭。

## 2. 部署组成

使用 `Dockerfile` 与 `compose.production.yaml`：

- `db`：独立 PostgreSQL 数据卷，不发布宿主机端口。初始化建立非超级用户、不可建库/建角色的应用账号，管理员密码只交给数据库和备份服务。
- `migrate`：一次性、幂等迁移，成功后 Web/Worker 才启动；迁移失败阻止启动，不自动植入演示或个人数据。
- `web` / `worker`：分别运行生产产物，以非 root 用户运行，只读根文件系统、临时目录、收紧容器权限；各自健康检查、日志轮转、进程退出后自动重启。
- `proxy`：Caddy 对外提供 80/443，自动 HTTPS，转发 Web；业务请求体上限 128 KB，不保留原始访问日志，运行错误日志过滤请求 URI 和请求头，避免记录 OAuth 回调参数和 Cookie。
- `backup`：每天导出一份可列出的 custom-format 数据库备份及校验和，默认保留 7 天；只有成功完成才更新时间标记，失败一小时后重试，超过 30 小时无成功备份标记为 unhealthy。

当前按**一个 Web、一个 Worker、一个数据库**的邀请试用部署验证。业务限频使用共享数据库，但认证限频仍是单 Web 进程的内存状态，Worker 健康依赖当前单实例心跳；不要把增加副本当作已验收的横向扩容。

Docker 的健康检查表示状态，不会自动重启一个仍在运行但 unhealthy 的容器；需要外部监控健康和告警，不能把 `restart: unless-stopped` 描述为完整故障自愈。

## 3. 首次上线

准备一个能访问所用 GitHub、Google 和可选模型服务的 Linux 主机，安装 Docker Engine / Compose v2。将域名解析到服务器，允许公网访问 80/443；不公开 PostgreSQL、应用内部端口或 Docker 控制接口。这里不假定本机的代理端口在服务器可用。

上传项目源文件即可，不复制个人 `.env.local`、本机数据库或 `work/`。构建忽略环境文件、备份、测试输出、本机 Skill 和 Git 目录；配置文件保留在服务器主机，权限应仅允许运维账号读取。

安装 Node.js 24 后运行以下命令生成配置；也可以用 Node 24 容器执行同一个脚本。域名和数字 ID 是填写示意：

```bash
node deploy/prepare-env.mjs https://news.your-domain.example 123456,789012
```

脚本生成 `deploy/server.env`，使用互不相同的随机数据库管理员密码、应用密码和认证密钥；不会输出秘密，也不会覆盖已有文件或自动轮换旧密钥。Linux 下文件权限为 0600；该文件被 Git 和 Docker 构建忽略。

编辑此文件，填入服务器专用 GitHub OAuth 客户端和密钥。普通试用用户只需在浏览器登录，不需要填写服务端密钥。建议生产与本机使用不同的 OAuth 客户端，避免修改回调后破坏本机联调。

回调分别为：

```text
GitHub:  https://你的域名/api/auth/callback/github
YouTube: https://你的域名/api/platforms/youtube/callback
```

需要让其他用户连接 YouTube 时，再填写 Google OAuth 客户端和密钥，并核对 Google 控制台的发布状态、授权范围与可授权用户名单；本机个人授权成功不能替代这个服务器配置检查。YouTube 内容生命周期仍保留未验收状态，不宣称正式平台接入认证已经完成。

所有以下命令都在仓库根目录执行，并使用同一份配置和 Compose 文件：

```bash
docker compose --env-file deploy/server.env -f compose.production.yaml config --quiet
docker compose --env-file deploy/server.env -f compose.production.yaml build
docker compose --env-file deploy/server.env -f compose.production.yaml up -d --wait
docker compose --env-file deploy/server.env -f compose.production.yaml ps
curl --fail https://你的域名/api/health/ready
```

不要用 `docker compose config` 的完整展开结果或 `docker inspect` 的环境部分制作截图，这些内容可能含秘密。`config --quiet` 只校验而不展开打印。`up --wait` 通过也不证明公网域名、证书和 OAuth 回调已正确，仍须从服务器外访问并实际登录。

新服务器使用空库，各受邀用户自行登录、导入关注；不把开发者本机账号和阅读记录复制给试用用户。

## 4. 上线后检查

1. 浏览器访问 HTTPS 域名，HTTP 应跳转 HTTPS；登录 Cookie 为安全属性，页面和业务 API 不经过共享缓存。
2. 用两个不同 GitHub 账号登录。各自只看到自己的来源、阅读状态、偏好和任务；未加入邀请名单的账号被拒绝。
3. 两个账号分别添加少量来源、等待同步、阅读、收藏和修改设置；切换账号后状态不串用。
4. 若开放 YouTube，使用两位受邀用户分别授权、读取关注、导入和同步，记录提供方配置及真实网络结果；不要求用户发送令牌、回调地址或服务器密钥。
5. 检查 Skill 页面只出现 GitHub Star 来源，直接访问本机 Skill 接口也应拒绝。API 限频或 AI 总预算耗尽时，原有内容仍能阅读。
6. 检查 ready 中数据库/迁移 ready、Worker online，并确认首次自动备份、一次隔离恢复和数据库角色检查通过。
7. 在手机、弱网及多位用户同时阅读/同步时观测响应时间、错误率、队列等待、CPU/内存、数据库连接和 API 配额，再决定扩大邀请范围。现有本机数据不是服务器并发容量承诺。

## 5. 备份与隔离恢复

自动备份位于独立的 Docker `backups` 卷。它与数据库卷分开，但仍在同一台服务器，**不是异机容灾**。完整 dump 包含会话、账号和加密 OAuth 凭据，必须按敏感数据保管。认证密钥另行安全备份；不要因 dump 中令牌加密就公开整个备份。

主动生成备份：

```bash
docker compose --env-file deploy/server.env -f compose.production.yaml run --rm --no-deps backup once
docker compose --env-file deploy/server.env -f compose.production.yaml exec -T backup ls -1 /backups
```

选择刚生成的 `news-时间-编号.dump`，在下面替换完整文件名：

```bash
docker compose --env-file deploy/server.env -f compose.production.yaml exec -T backup sh /opt/restore-drill.sh /backups/news-实际文件名.dump
```

演练先验证校验和，只创建随机命名的 `news_restore_drill_*` 临时库，拒绝使用已存在的目标，检查最新迁移与条目用户引用并报告计数；不会恢复覆盖 `news`。创建前登记清理责任，正常退出、创建失败或常规信号取消都会尝试清理。强制杀死容器/断电时 trap 无法保证执行，恢复后应核查该前缀的残留库，确认是本次演练生成的目标后单独清理；不要按宽泛模式自动删除库。

演练证明指定 dump 能恢复并通过结构检查，不声称与仍在更新的源库此刻逐行相同。正式故障恢复应先停写、保留现状并恢复到新目标，再验证和切换，不在本脚本中提供覆盖生产库的一键操作。YouTube 删除记录的恢复重放仍属于暂缓的生命周期工作。

定期将备份复制到权限受控的目录，再加密传到另一台机器或对象存储；不要只依赖同一主机数据卷。不要执行 `down -v`、卷清理或磁盘清理来解决普通重启问题。

## 6. 更新、邀请变更与回滚

- 修改邀请名单或 OAuth/模型设置后，使用同一配置文件执行 `up -d --force-recreate web worker`，使 Web、Worker 一起应用新配置。移除邀请不等于删除其平台数据，也不撤销提供方授权。
- 数据库已初始化后，修改环境文件中的密码不会自动修改已有 PostgreSQL 角色密码。不要重新运行配置生成器或随意替换 `BETTER_AUTH_SECRET`；旧 OAuth 凭据会因认证密钥变化而无法解密。
- 发布前主动备份；为新版本设置独立 `APP_IMAGE_TAG`，先构建再停 Web/Worker，运行新版本迁移并重新启动。保留上一个镜像标签、配置和备份，不使用每次覆盖后无法区分的标签作为唯一回滚方案。
- 回滚前确认迁移向后兼容；失败迁移或不可逆结构变化应采用核验过的备份/前滚修复，不自动向下删表。
- 用 `ps`、健康接口和脱敏的 Web/Worker/backup 日志定位问题；不得在公开 Issue、截图或聊天中发送配置、Cookie、完整 OAuth 回调、dump 或账号行。
