# GitHub 项目与博主关注规则

更新日期：2026-09-13。用户确认先做好 GitHub：Star 项目看项目更新，关注博主看博主更新。本轮不扩展其他平台，不增加邮件。

## 跟踪范围

| 关注对象 | 收录内容 | 默认排除 |
| --- | --- | --- |
| 项目（含自动导入的公开 Star） | 正式 Release，以及已收录 Release 的说明修改 | 草稿、预发布、提交、PR、Issue |
| 个人开发者 | 本人拥有的新建公开非 fork 仓库及 README；本人发布的正式 Release，包括组织或其他人的公开项目 | Star、评论、提交、PR、Issue、fork、他人或机器人发布的版本 |

「本人发布」以 GitHub 公开 `ReleaseEvent` 的 `actor.id` 匹配订阅保存的稳定账号 ID，且 `action=published`。不以仓库 owner 或 `release.author` 判断：后者可能只是草稿创建者。机器人代发的版本不自动归给博主；要持续关注整个项目，应直接订阅仓库。

事件中的版本信息可能是旧快照，因此先读取项目当前公开状态，再按版本 ID 读取当前说明；忽略已变私有、已删除、草稿或预发布目标。限流、授权和网络错误保留为可见失败，不伪装成无更新。

## 页面行为

- 更新列表和详情显示「订阅项目 · owner/repo」「关注博主 · login」等来源。
- 同一版本同时匹配项目和博主只显示一次，从任一订阅的「查看更新」均可找到。
- 订阅卡片就地说明跟踪范围；达到公开事件窗口上限时显示提示。
- 来源合并不重新生成已有摘要或译文；原文发生变化时清除过期 AI 产物并按既有规则排队，保留已读、收藏和首次收录时间。
- 删除其中一个订阅不删除已收录消息，剩余订阅仍可查看；重点来源命中任一个当前订阅即可生效。
- 中文摘要与按需逐条对照翻译沿用现有实现，当前模型配置不变。

## 采集与持久化

项目订阅使用版本列表；个人订阅分成「新仓库」「发布事件」两条流。版本列表/新仓库沿用原游标键，个人发布使用独立游标。两条流都扫描完成才更新最后成功检查时间；失败时保留已完成页和 partial 状态，下次从失败页继续。

用户内的事件身份为 `type:externalId`；数据库事务按稳定顺序取得事件锁，再合并 `sourceIds`。兼容已有 `sourceId`，不需要 SQL 迁移。行锁保留其他并发写入，版本 `updated_at` 阻止迟到的旧正文覆盖新正文。每页入库前确认订阅仍启用，提交前再次检查取消信号。

历史补查只考虑订阅创建前最近 30 天，每条流最多 20 个历史候选；个人两条流分别计数。重复扫描中的已知候选也占计数，避免逐轮扩张历史导入。已收录条目可继续检查正文修改，包括已超出初次历史窗口的项目版本。历史条目不进入近期简报。

## 覆盖限制

GitHub 公开事件接口只提供最近 **30 天、最多 300 条事件**，此上限包括所有活动，并非 300 条 Release。每页 100 条、最多 3 页。GitHub 官方说明事件可能延迟 **30 秒至 6 小时**；应用默认作者轮询间隔另为 30 分钟，因此不承诺即时消息或固定最大到达时间。

高活跃账号的版本事件可能在两次检查间挤出窗口，历史缺口无法保证补回。只关注个人时，旧发布事件离开窗口后也无法保证继续检测该版本说明修改；需要此能力请订阅对应项目。完成状态仅表示已扫描可访问窗口，不表示覆盖 GitHub 全部活动。

项目扫描每次最多 5 页，未完成时保存页码并续扫。大量版本的仓库需要多轮才能扫描完全部页，说明修改也可能延后发现。账号改名迁移、项目转移/删除通知、完整 following 分页和长期连续试用仍是后续事项。

官方依据：

- [Events REST API](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- [ReleaseEvent 定义](https://docs.github.com/en/rest/using-the-rest-api/github-event-types#releaseevent)
