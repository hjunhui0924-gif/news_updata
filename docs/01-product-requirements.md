# 产品需求 · 本地 MVP

更新日期：2026-09-13。本文件描述当前实现，替代初版包含邮件的方案。

## 用户与核心流程

产品核心需求是在一个网页集中阅读自己关注的信息来源更新，减少跨应用、跨页面检查和阅读的成本。当前阶段按用户决定先做好 GitHub，再接入其他平台；跨平台仍是后续方向，不能把当前单平台 MVP 描述为已经完成聚合目标。

GitHub 阶段面向希望追踪开发者和开源项目的个人用户。打开网页即可知道关注对象有哪些受支持的新变化，阅读正文、摘要或对照译文，并保存阅读状态。AI 辅助理解，Trending 辅助发现；关注更新的可靠同步和站内阅读是主流程。

1. 演示模式进入网页；真实模式通过 GitHub OAuth 和稳定用户 ID 允许名单登录。
2. 添加 `owner/repo` 订阅正式版本发布，或添加个人账号发现新仓库和本人发布的正式版本。
3. 后台轮询抓取公开数据并去重；开启 AI 后自动生成新条目摘要。
4. 在详情切换中文摘要、对照翻译和原文。全文翻译由点击触发。
5. 在设置页生成近期未读更新的站内简报。没有邮件配置或发送流程。

## 更新的定义

| 来源         | 包含                                     | 不包含                                             |
| ------------ | ---------------------------------------- | -------------------------------------------------- |
| 仓库订阅     | 正式 Release 及已抓取 Release 的正文变化 | 草稿、预发布、普通 commit、PR、Issue               |
| 个人账号     | 其拥有的新建公开非 fork 仓库及 README、本人发布的正式 Release（含组织项目） | 他人或机器人发布的版本、参与仓库的全部活动、星标、评论 |
| 关注列表导入 | 输入用户的公开 following，勾选为作者订阅 | 自动订阅所有作者仓库的版本                         |

从作者发现项目后，可手动把仓库添加为 Release 订阅。GitHub 账号改名后的自动迁移、转移与删除检测未专项实现。

个人发布归属按公开 `ReleaseEvent.actor.id` 判断，不把仓库拥有者或 Release 草稿创建者当成实际发布者。同一 Release 命中项目和个人订阅时只显示一次，保留全部匹配来源，可从任一订阅查看。详情见 [GitHub 关注规则](11-github-following-scope.md)。

## 阅读与提醒

- 今日精选：独立的 GitHub Trending 每日热门发现，全部领域，支持常用编程语言榜单；按来源榜单顺序显示，不使用个人 Star 列表作为精选来源。可按需翻译简介、订阅正式 Release。
- 全部更新：可按类型、来源、未读筛选并搜索标题、仓库、描述和标签。
- 收藏和已读持久化，后台更新原文时保留状态。批量已读只作用于当前筛选结果。
- 列表首次展示 20 条，再点击加载更多；MVP 后端一次返回个人全部条目，服务端分页后置。
- 站内简报：近 7 天未读、未屏蔽、非历史补查条目，重点优先，最多 10 条；不额外调用模型。
- Web 自动刷新：有活动任务时约 1.5 秒，无任务时约 30 秒。必须保持 Worker 运行才会自动采集。
- 关闭网页后 Worker 仍可同步；没有邮件、系统推送或浏览器通知。

## AI 输出约束

输出中文结论、最多三条变化、影响及升级留意事项，附带编号原文片段。推测影响需标注，未明确说明的兼容性显示未知。结构与引用校验不能证明语义完全正确，读者始终可以核对来源。

原文参与摘要的上限为 16000 字符；全文翻译超过 16000 字符时明确拒绝，不静默返回截断译文。README 最多保存 60000 字符。真实模型默认关闭，固定示例不计费。费用按配置单价估算，设置日/月上限。

## 数据覆盖和试用上限

- 每个用户最多 100 个仓库订阅、50 个作者订阅；following 预览前 50 人，超出时有提示。
- 历史内容限制为订阅创建前最近 30 天，每条采集流最多 20 个候选（项目为版本流，个人分新仓库和版本两条流）。已收录条目仍可检查正文修改。历史内容保留标识，不进入简报；今日精选独立读取 Trending。
- 每次同步最多 5 页，未完成页码持久化，后续同步继续。
- 个人发布动态最多读取最近 30 天、300 条公开事件（不是 300 个版本），最多 3 页。GitHub 事件接口可能延迟 30 秒至 6 小时，窗口外的发布无法保证补回；只关注个人时不保证长期追踪旧版本说明修改，需要持续跟踪某个项目时应订阅项目。
- 仓库默认每 15 分钟、作者每 30 分钟轮询，可在服务端配置。
- 429 等限流记录等待期限；401/404 暂停来源。覆盖状态表示本应用的扫描进度，不承诺 GitHub 所有活动完整性。

## 验收边界

本次目标是可运行、可操作、经过模块与浏览器测试的本地 Demo。真实 GitHub 公开读取已连通；真实 OAuth 登录与收费模型需要用户自己的凭据。跨平台、邮件、商业化、公开部署与长期连续运行不属于本次 MVP 完成条件。

用户进一步确定的推进顺序为：先完善 GitHub 的关注管理、更新同步和站内阅读，再考虑其他平台。当前技术测试通过不等于长期使用可靠性已经验证；下一阶段范围和准入条件见开发路线。

## Star 跟踪增量

已支持读取当前登录账号的公开 Star 仓库并勾选导入为 Release 订阅。真实模式默认每 5 分钟自动检查新增 Star，也可手动立即检查或关闭。列表可分页，导入幂等并支持部分失败重试；取消 Star 不自动取消订阅，在应用内取消的订阅不会被自动加回，手动再次导入可解除排除。完整规则与实测结果见 [Star 跟踪](08-starred-tracking.md)。
