# 聚合阅读器前端重构方案

规划日期：2026-11-05。状态：R0–R7 已完成本轮 Demo 阶段验收；真实 YouTube 授权、关注读取、频道导入、首次同步、站内数据读取与访问凭据自动续期随后通过，完整平台内容生命周期仍有实现缺口，持续同步、真实简介翻译与撤销后重连待验证，证据见 [真实闭环与生命周期验收](25-youtube-live-acceptance.md)；G4 用户试用仍未验收。交互草图位于 `docs/designs/aggregation-v0/`，用独立 React 页面表达信息架构和视觉方向，不连接项目 API、账号或数据库。

## 1. 背景与目标

现有应用围绕信息流、未读、收藏、平台、订阅来源和 Skill 等多个入口逐步扩展。作为聚合阅读产品，主导航应首先回答「有哪些值得读的更新」，而不是先展示工具目录。第一版草图已把 Skill 移到次级工具区，但“全部信息流”仍把大幅封面卡、双列内容卡、不同平台条目和右侧概况栏同时摆在首屏，内容优先级不清，跨平台来源也不够容易扫描。

本轮方案要把产品呈现收敛到「发现更新 → 判断来源和内容类型 → 阅读或稍后处理」这条路径。用户能快速看出条目属于哪个平台、哪个来源、什么类型、何时更新；切换 GitHub / YouTube 后仍沿用同一套阅读规则。页面要清楚、安静、稳定，兼顾桌面连续浏览和手机单手操作。

本次是前端信息架构和体验重构，不是新建平台能力。保留现有 Next.js、React、服务端接口、数据模型、账号隔离、授权范围和同步行为。不得把 YouTube 实际 OAuth 标记为已验收；不得在这轮重新开始用户已暂停的授权联调；G4 仍等待真实持续试用。

## 2. 参考产品与设计判断

### New API

参考 [QuantumNous/new-api](https://github.com/QuantumNous/new-api) 管理界面的结构特点：固定导航、明确选中态、紧凑顶部栏、轻量边框、统一控件和内容区的清楚层级。借鉴的是后台信息组织与视觉秩序，不复制它的品牌、配色细节、管理业务或组件代码。信息流是阅读产品，不能把它做成指标仪表盘。

### 聚合阅读器草图

当前草图对照了信息流、未读、收藏、来源管理、单条阅读和移动导航。已发现“全部”不能继续用一个突出故事卡加多列卡片来表达：那会让卡片面积和图片决定优先级，也让 GitHub 更新与视频看起来像不同产品拼在一起。统一时间流通过一致的行结构呈现共同字段，并把来源类型留作可识别标记。

草图中的内容、数量、连接状态、日期和阅读时长均为虚构演示值。封面只是版式素材，不代表实际平台截图。草图不应被当作生产行为或 YouTube 授权成功的证明。

## 3. 信息架构

主导航围绕用户的阅读任务组织：

| 一级入口 | 含义 | 交互要求 |
| --- | --- | --- |
| 信息流 | 所有已导入来源的更新，默认入口 | 时间倒序；保留平台、来源、未读等筛选；进入条目详情后可回到原位置 |
| 未读 | 当前未读条目 | 阅读后及时更新计数；空状态可返回信息流 |
| 收藏 | 用户主动留存的条目 | 与已读状态独立；来源删除或取消关注不能悄悄清除收藏 |
| 平台 | 已连接或可用的平台入口，例如 GitHub、YouTube | 只展示能力和状态真实支持的操作；连接状态与历史内容可读状态分开 |
| 订阅来源 | 用户实际导入的仓库、频道或作者 | 可按来源查看；来源管理、导入和同步状态放在同一入口 |
| 更多工具 | Skill、发现等非核心阅读能力 | 不挤占阅读主导航，不将发现结果混入个人关注的信息流 |
| 偏好设置 | 显示、阅读和账号偏好 | 复用已有设置能力，不另造一份设置存储 |

桌面端采用 New API 式的固定左导航和轻量顶部栏；主要操作放在内容区顶部。手机端左侧导航改为抽屉，底部只保留信息流、未读、收藏、来源四个常用入口。平台和单个来源可从信息流过滤器或来源页面进入，不将侧栏扩展成无限长的账号列表。

## 4. 信息流规则和页面层级

### “全部”默认视图

1. 全部来源按发布时间倒序合并，采用同一条时间线。平台差异体现在平台标识和内容类型，不通过彼此不一致的卡片模板制造多个视觉层级。
2. 时间线按「今天 / 昨天 / 更早日期」分组。分组只用于定位，不改变后端顺序；同一时间戳用稳定 ID 作次序键，避免新条目插入时列表抖动。
3. 每条更新使用一致的紧凑结构：平台图标和名称、具体来源、内容类型、时间、标题、短摘要、分类/阅读估时、已读状态与收藏操作。标题和来源必须可读；平台不能只靠颜色辨认。
4. 默认列表不设唯一“头条”，不使用不同尺寸的多列混排，不在信息流旁重复展示订阅总览和收藏预览。页面首屏优先展示可扫描的更新条目。
5. GitHub 更新与 YouTube 视频保留各自的内容语义。视频条目标明「视频 / 简介」，只展示已取得的元数据并提供原站入口；不把简介伪装成字幕、全文或 AI 视频摘要。
6. 仅在真实数据有可靠图片时显示有固定比例和占位的缩略图；图片失败不改变行高。默认文字流不依赖图片理解来源或内容。

### 筛选和排序

- 平台筛选采用「全部 / GitHub / YouTube」等明确选项；数量口径说明为当前筛选内总数或未读数，不能混用。
- 来源筛选、未读、收藏和搜索可组合。筛选后保留查询条件和滚动上下文；清空条件有明确入口。
- 默认按发布时间最新优先。其他排序只有在当前数据字段可靠且有真实使用价值时加入；不得用缺失的来源更新时间伪装成精确排序。
- 「全部已读」的影响范围与当前筛选一致，并提供即时反馈和可撤销能力（若现有状态/API支持）；不能静默将整个账号所有平台标记已读。
- 当前结果数、未读数、收藏数使用一致的定义。过滤后为零、账号无来源、来源暂时同步失败、平台尚未连接均提供对应空态和下一步操作。

### 阅读详情

- 列表进入详情时保留平台、来源、原始时间、原站链接和类型信息；返回时恢复原筛选、滚动锚点和布局。
- GitHub 文本保留原文、现有 AI 摘要/翻译与证据能力。原文持续可读；AI 失败、关闭或超预算不阻断阅读。
- YouTube 详情按当前实现提供可验证的标题、简介和原站入口。不下载音视频、不抓字幕、不转写；真实账号关注读取仍是暂停验收项。
- 分栏阅读是桌面可选模式；窄屏详情切换为全屏阅读页并提供清晰返回操作。已读和收藏状态与列表一致。

## 5. 视觉、交互和无障碍

- 采用白色内容表面、浅中性色背景、细边界、少量蓝色强调和稳定的字号/间距层级。为读屏、焦点和对比度提供明确状态，颜色不单独承载语义。
- 页面标题、筛选、主要操作、内容列表按这个顺序组织。删除没有决策用途的装饰数字、宣传语、重复说明和抢占阅读空间的侧栏模块。
- 主要操作使用图标加文字；收藏等单一操作使用具名图标按钮和 tooltip。筛选使用可识别的选项控件，布局模式使用分段按钮；避免仅依赖 hover。
- 键盘可到达导航、筛选、条目、收藏和详情返回；焦点清晰。对话框支持 Escape、焦点圈定及关闭后焦点还原。异步错误使用可读文字和可执行重试动作。
- 支持 320px 起的窄屏、系统 reduced motion 和浏览器缩放。长标题、长来源名、无摘要、超长简介、缺图和高对比主题不得让控件互相覆盖或产生横向溢出。
- 桌面阅读区控制最大行宽；手机端减少不必要元信息，但不得隐藏来源、平台、标题、时间或收藏操作。

## 6. 数据与性能边界

重构优先复用当前 API 和客户端数据层。已实现的信息流 `(published_at,id)` keyset 分页、每页上限 30、轻量 `FeedPreview`、详情按需读取、搜索索引、请求取消/竞态保护和有限分页缓存必须作为现有能力核对后沿用。列表不请求完整正文、AI 结果或媒体内容。不得为了简化界面新增全量拉取或高频轮询。

实现前按当前代码重测首屏请求、过滤/搜索、详情请求、已加载条目数、主线程长任务、滚动和内存趋势，并记录设备、浏览器、数据规模、冷/热缓存和重复次数。先优化组件重复渲染、图片占位、稳定 key、无效状态派生和加载反馈。保留已验证的原生分页与 `content-visibility`。只有在真实目标数据下 CPU/DOM/内存瓶颈可重复出现时，才单独试验虚拟列表；试验必须验证变高行、键盘查找、焦点、读屏、滚动锚点、图片加载及返回详情，并可独立撤回。

滚动时后台同步不得把新内容插入当前阅读位置。延续“有新内容提示，由用户选择刷新”的连续性规则；刷新后避免重复、丢失已读/收藏或跳动。设置合理的最大缓存与预取范围，遵守现有用户隔离和取消行为。

本轮不增加 Redis、额外搜索服务或新的 UI 框架；不为视觉重构变更数据库 Schema。新增依赖须先证明现有 React/Next.js 和组件不能满足需求，再评估包大小、维护状况、许可和兼容性。

## 7. 状态矩阵

| 场景 | 用户可见结果 | 数据与恢复要求 |
| --- | --- | --- |
| 首次进入 / 尚未添加来源 | 说明个人信息流目前为空，给出连接平台入口 | 不显示虚假“成功连接”状态 |
| 正在加载首屏/下一页 | 稳定占位，不让顶部操作或已有条目跳动 | 支持取消过期请求，分页不重复 |
| 当前筛选无结果 | 说明是无更新、无匹配还是筛选过窄，并提供重置筛选 | 不清除用户原搜索词 |
| 某平台未连接 | 显示准确连接状态和受支持动作 | 不影响其他平台和历史内容阅读 |
| 同步失败/限流/过期 | 显示简明原因、最后成功同步时间和可行恢复动作 | 保留已有内容；遵守 retryAt/Retry-After；不要求网络错误重新授权 |
| 搜索/筛选快速切换 | 只显示当前条件结果 | 旧响应不能覆盖新状态；保持稳定结果计数 |
| 收藏/已读更新失败 | 保留当前列表上下文并告知失败，可重试 | 服务端状态为准，防止并发响应回滚最新状态 |
| 详情原文/摘要/译文缺失 | 明确缺失原因或生成状态，仍可读已有内容 | 版本、证据与缓存校验复用当前实现 |
| 图片缺失/加载慢 | 保留固定占位和完整文字信息 | 懒加载、不预取媒体、不改变滚动锚点 |
| 手机抽屉/详情 | 抽屉可关闭；详情全屏并提供返回 | 焦点、筛选与列表位置恢复 |

## 8. 分阶段实施与逐项 Review

每阶段先核对入口和当前行为，再按风险选择检查深度。接口契约、数据隔离、并发状态、分页/游标和批量操作需要专项 review 及针对性测试；确定性样式和布局改动以类型检查、Lint、目标视口和关键交互轻检为主。发现问题后修复并复验，再更新本文状态；重要问题未解决不得进入依赖它的阶段。性能证据按改动影响采集，不要求每个样式步骤重复全量性能测试。

| 阶段 | 工作范围 | 主要验收 | 状态 |
| --- | --- | --- | --- |
| R0 基线和页面盘点 | 记录生产路由、组件、数据接口、现有测试与当前桌面/手机性能；对照概念草图标明可复用和不可替换能力 | 所有现状均有文件/API/测试依据；列出变更风险，不重复开发已完成能力 | 完成 |
| R1 视觉基线与应用壳层 | 统一 token、桌面侧栏、顶部工具栏、窄屏抽屉/底栏、焦点和页面宽度 | 原有入口仍可达；多视口无溢出；导航激活、关闭和返回状态正确 | 完成 |
| R2 聚合信息流 | 实现全平台统一时间流、日期分组、来源/平台/类型元信息、平台/来源筛选和空态 | 混合 GitHub/YouTube 顺序稳定；来源明确；过滤组合、计数和零结果一致 | 完成 |
| R3 搜索、未读和收藏 | 对接现有搜索与状态 API，统一计数和操作反馈，处理并发响应 | 当前筛选下全部已读范围正确；收藏与已读相互独立；失败可理解/重试 | 完成 |
| R4 阅读详情和返回连续性 | 将已有详情、Markdown、摘要、译文、视频简介融入统一阅读层级 | 返回恢复筛选/位置；AI 不阻断原文；视频内容标签准确；原站链接保留 | 完成 |
| R5 来源与平台状态 | 整理账号连接、关注导入、来源管理和同步状态界面，沿用现有业务流 | GitHub 流程不回归；YouTube 页面只反映已验证能力；状态不混淆历史可读性 | 完成 |
| R6 可访问性和响应式收尾 | 完成键盘、语义、焦点、触控、缩放、reduced motion、长内容和异常状态 QA | 320/390/768/1280/1440px 及窄高窗口通过；无横向溢出/遮挡 | 完成 |
| R7 性能与交付门禁 | 与 R0 同场景对照 API 请求、载荷、渲染、滚动、内存和完整回归；更新开发和验收文档 | 无退化或退化有明确修正；构建、类型、lint、单测、相关 E2E 和运行冒烟通过；review 无未解决重要问题 | 完成 |

## 9. 草图验收与边界

本方案写入时，交互草图已实现“全部”统一时间线、日期分组、平台/来源标记和无右侧重复概况栏；草图的筛选、收藏、详情、键盘入口及手机导航仅为本地样例行为。完成草图浏览器验证不等于生产页面重构通过，也不替代 R0 基线和后续阶段的 review。

R0–R7 的 Demo 阶段交付门禁已完成。用户随后明确恢复真实 YouTube 授权联调，授权及自己的关注读取已通过，频道导入、同步与真实账号生命周期仍待验收，详见 [YouTube 账号关注记录](19-youtube-account-following.md)。不得将模拟数据或 OAuth 模拟测试写成真实账号验收；G4 真实用户试用未发生前不得宣称用户体验已验证。
