# 聚合阅读器优化开发方案

日期：2026-11-04。状态：实施中、逐项验收；实际进度和验证证据见 [实施记录](21-aggregation-optimization-progress.md)，下列规划不代表功能已经完成。

适用项目：知更 / NEWSROOM。本方案基于当前 GitHub、YouTube 适配代码，以及 Folo、RSSHub、YouTube RSS Manager、Miniflux、Vao2 的官方资料和部分源码。目标是在现有 Demo 上提高可靠性、浏览流畅度与平台扩展能力，不重做已有阅读器。

## 1. 产品目标与明确边界

核心路径是「连接自己的平台账号 → 读取自己的关注 → 选择导入 → 持续获取更新 → 顺畅阅读」。平台搜索不属于本轮新增范围，已有 GitHub 搜索保持现状。

- 保留 Next.js Web、独立 Node Worker、PostgreSQL / pg-boss 的现有组成。没有测量证据前，不增加 Redis、消息中间件、独立搜索服务或微服务。
- 沿用站内身份、平台账号连接、来源、订阅、更新条目的既有定义；Google 连接不创建另一套站内身份，不按邮箱自动合并账号。
- GitHub 正常使用优先。单个平台、模型或 Worker 故障不能阻断已有内容阅读。
- 已读、收藏、屏蔽、来源归属及原站链接必须保留。源站取消关注不等于删除站内历史。
- 不增加平台搜索、推荐流、自动关注、源站写操作、邮件、音视频下载、字幕抓取或视频转写。
- YouTube 实际 OAuth 联调已经失败并按用户要求暂停。本轮可以完善通用错误分类与模拟回归，不能自行恢复人工授权排查，也不能用公开频道 RSS 冒充「读取我的关注」。
- G4 持续真实用户试用继续暂缓；自动化、性能实验和上游项目的成功案例均不能替代 G4。

### YouTube 的准确状态

用户已配置自己的 OAuth 客户端并尝试 Google 登录/同意授权。最近一次诊断确认站内会话、授权 Cookie、state 匹配和回调主机检查通过；待处理授权记录被消费，后续处理返回平台类 503，未保存连接凭据。尚不能确定是令牌交换、账号身份读取还是频道查询失败。

此前普通 Node 的连通性探测和模拟 OAuth 测试不证明真实连接成功。不得写成「密钥未配置」「只差用户点击授权」或「已接入可用」。临时调试代码已移除，问题以暂停项保留。

### 借鉴和源码复用的规则

1. 执行任务前记录上游仓库、文件、确切 commit、核对日期和所借鉴的行为。本次引用是查阅入口，分支链接可变化，不是已固定的依赖版本。
2. 先核对具体文件的 LICENSE、版权声明、第三方资产及依赖许可。没有明确许可时不复制源码；需要分发或提供网络服务时，另核对适用义务。仓库“公开”不等于可任意复用。
3. 优先写清行为、取舍与测试再自行实现。适配现有工程，不整包迁入桌面客户端、Python 服务或下载工具链。
4. 任何新增库都记录维护情况、版本兼容、运行时依赖、体积和替代方案；官方库也不能代替 state、PKCE、当前用户绑定及令牌生命周期验证。
5. 上游成功不等于本项目验证成功；未运行的能力写为“参考”或“待验证”。

## 4. 设计主线与可验证的改进提案

### 4.1 能力声明：允许平台不同，不制造万能连接器

沿用现有 `PlatformAdapter` 的来源解析、流定义、分页与内容补全。只有实际出现的差异才新增接口，不将授权、关注、AI、调度、数据库操作一起塞进适配器。

在工厂/注册处集中描述本项目需要的能力，例如：是否支持账号连接、个人关注、公开内容刷新、条件请求，以及实际支持的来源种类。字段命名和最终类型由 U1 确定，不能假定每个平台都支持 OAuth 或关注导入。

“适配器具备能力”与“当前账号可用”分开：已实现、已配置、已授权、临时不可用不是同一个状态。界面由能力和当前连接状态共同决定操作，不依据平台名称散落硬编码，也不把服务端内部错误直接展示给用户。

**改进提案：能力与数据新鲜度同时可见。** 用户能分别理解“来源支持什么”“账号能否读取”“现有内容更新到何时”，避免一个红色连接状态让用户误以为历史内容也不可读。

### 4.2 授权、关注发现、内容刷新分开承担失败

- 站内身份认证负责识别本应用用户；平台连接负责此用户的外部授权；关注发现只读取该连接的个人关注。
- 内容刷新仍通过来源适配器和 Worker。公开 Feed 只能在覆盖、身份和来源映射验证后成为可选读取路径，不能反向推断私人关注关系。
- 访问令牌续期、配置变化、权限不足、网络超时和用户取消要有不同的恢复动作；网络失败不一律要求重新授权。
- 若今后证实“只用于显示的频道名称读取”阻断连接，可评估降级为通用名称；必须身份与权限校验完整，不能跳过强制校验。当前没有证据证明它就是失败原因。

**改进提案：可恢复的错误回执。** 用户看到简短固定文案、下一步和不含账号信息的随机诊断编号；服务端只记录阶段枚举、错误类别、耗时、HTTP 状态及允许的网络错误码。不得记录 code、state、Cookie、令牌、PKCE verifier、完整回调 URL 或上游原始错误正文。

### 4.3 同步预算与阅读连续性

优先复用现有 pg-boss 和 PostgreSQL。根据 U0 测量，给平台同步、关注发现和 AI 分配有界工作量；避免一个慢任务占据全部处理机会，也不能简单增加并发耗尽数据库池与 API 配额。

缓存键至少考虑用户、平台、来源、读取范围和内容版本；账号相关缓存还要绑定连接版本。公共元数据是否共享必须另行证明不会混入私人关系或凭据。断开和账号切换后，旧请求不能重新建立连接或恢复失效预览。

**改进提案：稳定阅读快照。** 延续已有“新内容提示后由用户刷新”，把锚点定位、已加载页和在途状态操作一起验证。同步更及时不应造成阅读时卡片突然插入、跳位或重复标记已读。

### U0：先建立当前版本的可重复基线

**产出**：场景清单、当前代码版本、运行前提、原始报告位置、复测命令和初始瓶颈排序。

1. 核对已完成能力和历史验收，采用当前代码重测；历史 245 项测试或 600 条滚动结果不能当成本轮结果。
2. 扩展现有 `scripts/bench-feed.ts` 和浏览器性能场景，不另造一套互相矛盾的基准。脚本目前使用 12 次请求、去掉前 2 次预热，统计余下 10 次；后续报告应说明小样本限制，并支持至少 30 个稳定样本及多轮重复。
3. 覆盖混合类型、长标题/简介、图片失败、10,000 条数据库数据，以及 30 / 600 / 2,000 条已加载列表。超过日常规模的场景是压力实验，不自动扩大产品订阅上限。
4. 记录 API/SQL 延迟、载荷、外部请求量、队列等待、滚动帧间隔、长任务、上下文恢复和内存增长趋势。
5. 用假平台和假模型制造慢响应、限流、超时、断连，不消耗真实配额或修改日常数据。

**验收**：同一场景可重复执行，区分冷/热缓存和网络条件；输出至少一份当前基线。没有证实的问题进入观察清单，不能为了“完成优化”而更换实现。

**影响位置**：`scripts/bench-feed.ts`、`tests/e2e/hardening.spec.ts` 及新增的隔离性能用例。

### U1：集中平台能力，补齐安全诊断和恢复动作

**产出**：能力描述、用户可理解的连接/同步状态映射、固定错误分类、模块级测试。

1. 以 GitHub 和 YouTube 两个真实适配器检查最小接口；集中来源种类/能力声明，避免注册、校验与 UI 三处定义不一致。
2. 让不支持、未配置、未授权、临时失败、限流等待和数据过期具有明确区别；每个状态配套可执行动作与禁用原因。
3. 为请求链默认保留安全的阶段、分类、状态和耗时，详细调试默认关闭；任何模式都不记录秘密值。用模拟回调分别覆盖会话丢失、state 不匹配、过期、token 失败、身份失败和附加资料失败，证明日志不会泄密。
4. 比较继续使用现有 transport 与引入 OAuth 库的收益、迁移成本、Worker 兼容和测试接缝；记录选择理由，不预设“换 SDK 就会修复”。
5. 保留固定回调、同源写请求校验、最小权限、用户/连接版本绑定和续期锁；不得通过放宽检查消除报错。

**验收**：相同错误在页面上有一致含义；临时失败不会误导重复授权；第三方错误不能进入 URL、日志或页面。真实 Google 授权仍标记暂停，模拟通过只证明契约成立。

**影响位置**：`src/shared/platforms.ts`、`src/server/platforms/{contract,registry,youtube-auth}.ts`、`src/server/http.ts`、连接相关组件和测试。

### U2：后台同步公平性、冷却和缓存新鲜度

**产出**：慢任务影响报告、有界调度策略、必要的持久化冷却和任务恢复回归。

1. 先测量共享队列中慢 AI、慢平台对同步等待时间的影响，以及调度器扫描/逐来源查询的成本；只在存在瓶颈时改批量查询或队列分工。
2. 根据任务种类和平台设置工作预算、最大并发及超时；人工刷新可以提高调度机会，但不能绕过配额、去重和冷却，也不能永久饿死普通任务。
3. 对临时错误采用有界退避和必要的抖动；遵循允许的 Retry-After。可重试与需人工处理的错误分开，禁止无限重排。
4. 如需跨 Web / Worker 的统一冷却，按实际配额归属设计键：用户授权失效、账号限流、项目级配额不能相互误伤。使用 PostgreSQL 原子更新，验证重启后恢复，避免未经测量引入 Redis。
5. 保留分页检查点、条件请求及“首页 304 仍检查后续页”语义；不能用缓存命中率换取支持窗口内的漏抓。
6. 失败时继续提供已有内容，并展示最后成功时间、下一次可重试时间和覆盖范围。断开连接后不能以缓存命中为由继续个人关注请求。

**验收**：假模型持续变慢、单个平台失败和 Worker 重启时，其他已启用来源仍能在记录的预算内推进；同一目标只有一个活动任务；取消/重试不丢检查点，不产生重复条目。

**影响位置**：`src/worker/main.ts`、`src/server/jobs/queue.ts`、`src/server/subscriptions/service.ts`、平台 transport 和同步集成测试。

### U3：混合列表、长正文和滚动连续性

**产出**：现有实现与候选方案的同场景对比、必要的局部优化、桌面/移动/键盘回归。

1. 优先检查预览字段、稳定 key、重复渲染、图片占位、详情懒加载及缓存淘汰。不可为前端更快而一次返回完整正文或无限保留已加载数据。
2. 延续现有有限分页缓存和原生 `content-visibility`。只有长列表 CPU、DOM 或内存瓶颈可重复出现时，才试验 Folo 类虚拟化；实验可独立撤回。
3. 若引入虚拟化，验证变高卡片、图片加载、跨页追加、键盘定位、浏览器查找、读屏语义和滚动锚点；不能只比较滚动截图。
4. 返回详情、切换筛选后返回、浏览器前进后退和新内容刷新都恢复合理上下文；锚点对应条目消失时有确定的退让规则。
5. 大 Markdown 正文按测量决定拆分/延迟处理；保留安全渲染、相对链接解析、原文入口和翻译定位。不把“截掉内容”作为默认提速办法。

**验收**：达到第 6 节的实验门槛；收藏/已读等在途操作与淘汰、翻页并发时不回滚成旧状态；390px 无横向溢出，键盘可完整完成阅读流程。若当前实现已达标，可交付“不引入虚拟化”的证据结论。

**影响位置**：`src/components/{feed-list,use-feed,reader-app,item-detail,markdown}.tsx/ts`、`src/app/globals.css` 和浏览器回归。

### U4：关注导入保持选择、结果可解释、失败可继续

**产出**：GitHub / YouTube 共有交互规范、连接版本保护的回归、导入结果回执。

1. 复用已有分页、跨页选择、已订阅标记、名额限制、幂等导入与部分失败处理；不重新实现一个无用户隔离的通用批量接口。
2. 统一初次加载、加载下一页、空关注、部分失败、全部失败、预览过期、账号变化和限流等待的反馈。
3. 以“成功 / 已存在 / 失败待重试”解释本次结果，保留仍合法的未成功选择；账号改变或预览过期时明确重新读取，不能静默替用户提交旧选择。
4. 客户端可保留非敏感选择，但它不构成服务端授权依据；不把账号凭据或整个私有关注快照写进浏览器长期存储。
5. 丢响应后的重试不重复消费分页或创建任务；源站新增关注仍通过重新读取选择导入，取消关注不自动删订阅。

**验收**：跨页选择、丢响应、重复点击、名额竞争、账号切换、断开后旧请求返回均有集成/浏览器证据。GitHub 和模拟 YouTube 可以验收公共交互；真实 YouTube 关注读取单列暂停，不能合并为全平台已验收。

**影响位置**：`src/components/{following-import,starred-import,youtube-following}.tsx`、`src/server/platforms/youtube-following.ts` 和现有导入模块。

### U5：AI 可降级、版本一致、费用可控

**产出**：现有 AI 行为的退化矩阵和内容更新/任务中断回归；不扩大视频 AI 范围。

1. 默认可以直接读原文。AI 关闭、排队、预算不足、超时和供应商不可用时，列表、详情、搜索、已读和收藏不受阻。
2. 摘要、译文和依据绑定原始内容版本、语言、模型及相关提示词版本；模型切换或内容变更不能误用旧结果。沿用现有缓存与预算结构，先补验证再决定迁移。
3. 任务中断、重复投递和多请求竞争时，预算预留/结算可解释，不把成本不确定状态静默当作免费重试；不无上限自动重试付费请求。
4. 保持 GitHub 正文与 YouTube 简介的区别。当前不向视频元数据/简介提供“视频全文摘要”或伪造转写。
5. 只把必要内容发给已配置模型，保留来源和证据。外部正文/模型输出不能触发源站写入、改变订阅或发消息。

**验收**：假模型慢、失败、返回无效结构、内容中途改变和预算耗尽时，阅读闭环完整且账目可追溯；无新增视频全文任务；主流程性能不得因等待 AI 下降。

**影响位置**：`src/server/ai/`、`src/server/skills/ai.ts`、详情/翻译组件、预算和队列集成测试。

### U6：数据生命周期与可回退迁移

**产出**：跨来源一致性规则、迁移/恢复清单、必要的过期数据清理策略。

1. 来源身份继续使用用户 + 平台 + 来源种类 + 稳定外部 ID；保留历史 GitHub 键兼容。名称相同、标题相似或 URL 看似相近不能自动合并为同一事件。
2. 同一内容来自多个已验证来源时保留归属；未来若做“相似内容分组”，只改展示，不未经确认合并阅读状态或删除底层条目。
3. 区分源站编辑、暂不可见、明确删除、用户取消关注、站内删除订阅、断开账号。缓存保留/清理必须符合具体平台要求；先核对规则再启用，不默认永久存储，也不遇到一次 404 就删历史。
4. 待处理 OAuth、关注预览、过期诊断等短期数据具备 TTL 或清理机制。日常维护不能把仍需保留的收藏和阅读状态当缓存删除。
5. 每项迁移先在隔离测试库验证，再备份日常库；验证旧数据、唯一键、计数、阅读状态和回退流程。不可逆迁移以备份恢复和前滚修复为主，不承诺自动向下迁移。
6. 为未来 OPML/导出列出可表达与不可表达的语义：通用订阅文件不能完整保存 Release 跟踪、账号权限和 AI 证据。仅列接口需求，不在本轮默认开发完整迁移产品。

**验收**：新旧数据升级兼容、清理幂等、编辑不覆盖错误版本、恢复后订阅/条目计数与阅读状态指纹一致。断开账号不破坏历史；已确认的平台删除/保留规则另行验收，不用泛化规则替代。

**影响位置**：`src/shared/platforms.ts`、`src/server/db/`、`src/server/subscriptions/`、`scripts/database-maintenance.ts`、相关迁移与隔离集成测试。

## 6. 性能验证方法与初始门槛

下表为拟定的本地实验目标，不是已有成绩、真实用户指标或生产 SLA。U0 可依据可复现环境调整数值，但须在优化前记录理由，不能在失败后静默降低门槛。

| 项目       | 场景与拟定门槛                                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------- |
| 数据库查询 | 10,000 条隔离数据、热缓存下，列表 p95 ≤ 50 ms，元数据搜索 p95 ≤ 100 ms；同时记录冷缓存和 EXPLAIN                            |
| 预览载荷   | 30 条普通混合预览，UTF-8 未压缩 JSON 目标 ≤ 40 KiB；正文、译文和证据不进入列表载荷；极端字段单列报告                        |
| 本地交互   | 不含防抖、网络和外部服务等待的本地操作，至下一次可见反馈 p95 ≤ 200 ms；完整搜索链路另记总延迟                               |
| 滚动       | 600 / 2,000 条已加载混合列表，帧间隔 p95 目标 ≤ 25 ms；600 条场景相对新基线不得无说明恶化超过 20%；同时报告长任务与掉帧分布 |
| 阅读稳定   | 图片加载、加载下一页、轮询提示、详情返回不导致无意跳位；无丢失选中条目、重复已读和筛选串页                                  |
| 资源增长   | 连续 20 次筛选/详情往返后，缓存和任务数受上限控制；同一 GC/采样方式下内存趋势不持续单调增长，异常增长需定位                 |
| 后台公平   | 在单一假平台持续超时或假模型变慢时，记录其他平台的队列等待 p95，并验证工作预算及普通任务不饿死；阈值由 U0 当前任务上限确定  |

执行约束：

- 使用隔离 `_test` 数据库、临时用户、假平台和假模型；清理本轮数据，不恢复或重建日常库来跑测试。
- 覆盖 1440px、768px、390px；记录浏览器/Node 版本、硬件、电源状态、数据分布、压缩口径、缓存状态、CPU/网络限速参数。
- 每个关键场景至少 3 轮；报告样本数、p50/p95、失败请求和异常值，不能只展示最好一次。小样本 p95 不用于过度外推。
- 区分 SQL 时间、服务端处理、网络、客户端渲染和端到端体验。25 ms 的帧间隔门槛不等于宣称稳定 60 FPS。
- 保存脱敏原始报告到忽略目录；文档记录可复测命令和结论，不能只链接会消失的本机临时文件。

## 7. 必须覆盖的组合与故障场景

| 场景                                    | 期望行为                                                    |
| --------------------------------------- | ----------------------------------------------------------- |
| 一个平台未配置/失效，另一个正常         | 能阅读已有内容，正常平台继续工作，失败处给出明确动作        |
| OAuth 取消、过期、重放、换站内用户      | 固定安全反馈；不串账号、不保存错误凭据、不泄漏回调参数      |
| 切换平台账号后旧分页/导入返回           | 旧预览失效，无法提交到新连接；已成功订阅和历史保留          |
| 限流、Retry-After、项目配额用尽         | 有界冷却、恢复时间可见；不重复风暴，不错误封禁无关账号/平台 |
| Worker 重启、进程中断、outbox 重投      | 不重复创建条目/付费任务；断点和阅读状态保持一致             |
| 首页 304，但后页有修改                  | 后页仍按现有协议验证，不漏掉支持窗口内的修改                |
| 慢列表 GET、并发收藏 PATCH、新筛选 GET  | 旧响应不覆盖新筛选；计数和成员关系最终一致                  |
| 图片失败、超长文字、长正文、2000 条列表 | 页面可读、操作可达、滚动稳定；不靠隐藏内容或禁用键盘达标    |
| 模型关闭/超时/预算耗尽，正文同时变更    | 原文持续可读；旧摘要不写入新版本；费用状态可解释            |
| 清理缓存、断开账号、删除来源            | 分别按自身语义执行；不把收藏、阅读状态和平台凭据一起误删    |

## 8. 条件性扩展：不自动进入本轮开发

### E1：恢复真实 YouTube 账号联调

前提是用户明确恢复；本次“先暂停”的决定持续有效。届时先用 U1 的阶段化诊断复现最近的 503，再根据证据选择修复现有 transport 或替换局部 OAuth 实现，不重做完整账号体系。

必须重新人工验证实际授权、确实读取自己的关注、导入后的真实更新、凭据续期和撤销/重连。授权码是一次性的，不能盲目重放交换请求；网络超时后的不确定结果要按具体协议恢复。模拟测试和无凭据连通性探测只作为前置检查。

### E2：RSS / RSSHub 读取路径试验

完成核心优化后，再确认是否值得添加试验适配器。先选择一个公开、稳定、可控的来源，验证身份映射、字段损失、编辑/删除、去重和覆盖；保留正式平台 API 路径，不能静默更换来源或更换条目身份。

如允许用户输入 Feed 或网关地址，必须在启用前完成 SSRF 和不可信内容约束：协议/主机准入、禁止凭据 URL、私网/回环/链路本地及云元数据地址拦截、DNS 解析与每次重定向复核、超时/大小/解压限制、XML 外部实体禁用、HTML 清理。自建本地 RSSHub 若确需访问，使用管理员显式配置的可信网关通道，不通过放开任意私网 URL 实现。

RSSHub 的公共实例不作为默认可靠依赖；部署成本、Cookie 托管、路由维护与平台规则均需评估。此候选路径不能替代个人关注授权。

### E3：Bilibili

先核对当时的官方能力、平台规则、授权/登录方式、内容覆盖与维护成本。RSSHub 路由可作参考，不能因此承诺官方 OAuth 或永久可用。Cookie 若成为候选方案，必须单独定义获取方式、最小范围、加密、到期/撤销和服务端隔离；不复用 Google 的授权假设，不现在新增采集任务。

## 9. 每项 review、回退与结果登记

每项依次执行「核对入口证据 → 小范围实现/实验 → 相关验证 → 独立只读 review → 修复 → 复验 → 登记」。Critical / Important 问题未解决，不进入下一项。无需改动也必须给出场景与测量结论，不能为展示进度制造代码变化。

Review 至少检查：

- 借鉴行为是否适合网页 Demo，是否引入没有实际使用者的复杂接口或新基础设施。
- 是否改变账号隔离、来源身份、覆盖窗口、分页、已读/收藏、预算或既有 GitHub 行为。
- 错误动作是否能恢复，授权和第三方数据是否会进入日志/URL/浏览器长期缓存。
- 性能收益是否来自相同条件的测量，是否牺牲键盘、读屏、移动端、内容完整性或正确性。
- 新依赖、来源声明、许可、测试证据、迁移和撤回方案是否完整。

回退规则：一次只合入一个完整工作包；实验功能可关闭并回到原读取路径。新旧缓存键/数据格式需要明确版本策略，不能回退代码却继续解释不兼容数据。数据库操作先演练备份恢复，生产或日常库不使用测试库重置命令。上游不可用时保留最后可用内容及时间标记，不把原文阅读一起关闭。
